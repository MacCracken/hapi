# 2026-10-29 — P(-1) audit and repairs (1.7.0 → 1.7.1)

**hapi version**: scanned at **1.7.0** (cyrius 6.7.18), repaired in **1.7.1**.
**Auditor**: maintainer pass per CLAUDE.md Process P(-1). Fourteen read-only
finder units ran, one per subsystem or lens:

- cap-resolve, fslink-create, link-sync, unlink-rollback, adopt-backup, trail;
- manifest-fmt, cli-status, agnos-arch, memory, errors, refactor, docs, tests-ci.

Each finding went to two independent verifiers, one told to reproduce it and
one told to refute it. A completeness critic then set eight probes, and their
findings were verified the same way: 476 agents in all. Every finding repaired
here was constructed again in this tree as a failing test before its fix.
**Trigger**: the standing re-run rule. 1.5.0–1.7.0 touched path arguments,
syscalls and the trail format, and 1.7.1 was set aside for a deep pass
before further 1.x work.

> ⚠ **The capability boundary was open again, and had been since 1.1.1.**
> The resolver behind every containment check (F-015, F-045, F-046, F-051)
> dropped the first byte of each relative symlink text it followed (F-065).
> Every test that exercised the boundary planted an absolute link, so nothing
> caught it. Five of this pass's HIGH findings are again one idea: a decision
> made on a spelling, or on one package, where the kernel acts on where a
> path physically goes.

## Scope

All six P(-1) steps and the four threat classes, over the whole tree as
1.7.0 shipped. The audit checked `src/`, the tests, the CI and the docs, and
probed each of the following directly:

- upgrade replay against every release since 1.1.1;
- kill and SIGPIPE windows;
- the environment the trail path depends on;
- torn manifest reads;
- interactions between rows within a single run.

## Method

The bar is unchanged: a finding counts only with a **constructed failure**.

**The verifiers ran while /tmp was out of inodes, for part of the pass
(F-064).** Many could not run a command, so their verdicts rest on reading the
code alone. No verdict was taken as proof. Each finding repaired below was
reproduced in this tree, by a test that fails on 1.7.0, before it was fixed.

Each repair was **mutation-proven**: its regression test was run against the
reverted code and confirmed red. A survivor is either equivalent or not
reachable in the suite's environment; each is listed under *Mutation
survivors*. Concurrency is held by `scripts/concurrency-test.sh`, which
goes red on 1.7.0 (F-071).

The 243 raw findings deduplicate to about 120 distinct issues. They are
triaged by tier in
[`../development/issues/2026-10-29-p1-triage.md`](../development/issues/2026-10-29-p1-triage.md).
This pass repairs tier 1, containment and data loss. Tiers 2 and 3 are
scheduled as 1.7.2 and 1.7.3 (*Deferred*).

## Findings

### The test harness

**F-064 — the suites never removed their scratch directories (MEDIUM, fixed).**
Each `tests/hapi.tcyr` run left about 150 directories, around 2,600 inodes,
under `/tmp`. The 1.7.0 cycle's mutation, fuzz and audit runs left 273,948 of
them, and every process writing to the tmpfs failed with ENOSPC while 54% of
its bytes were free. Each suite now records what it makes and removes it
(`tests/scratch.cyr`), and its last group asserts that nothing of the run is
left. The removal never follows a symlink. Three tests used fixed `/tmp`
names, which two runs at once shared. A real flake: one run's cleanup deleted
the file the other was checking.

### The capability boundary

**F-065 — a relative symlink's text lost its first byte (HIGH, fixed).**
`_fsl_split` began at index 1, and `fsl_resolve_path` splits each followed
link's own text with it. So `../outside` was walked as `./outside`, and
`dotfiles/config` as `otfiles/config`.

The consequences, constructed:

- `link --force` replaced a file outside `$HOME`;
- `adopt` moved one into a package;
- `--root ~/trap` with `trap -> ../outside` was granted;
- an allowlist entry reached through a relative link granted a sibling it
  never named;
- under a `/home -> var/home` layout (Fedora Atomic), every target was
  mis-resolved;
- F-045 and F-046 reopened;
- a plain no-arg `sync` wrote outside `$HOME` through the relative links hapi
  itself makes.

It affected 1.1.1 through 1.7.0, on every target. The verifiers reproduced it
on the 1.1.1, 1.4.0, 1.6.0 and 1.7.0 binaries, and on the agnos build.

**The fix must not strand what those versions wrote.** Links made under a
relative symlinked parent have a text from the mis-resolved parent, and after
the fix `unlink`, `prune` and `rollback` refused them as user-mutated. The
upgrade probe measured that on 1.1.1–1.7.0 links: 254 of 736 fuzzed links,
in 121 of 280 layouts.

The fix keeps 1.7.0's resolver verbatim as `_fsl_resolve_path_legacy`, used
for one thing only: a fourth text that removal accepts as hapi's. That is the
F-046 precedent, in the ADR 0003 addendum. Creation and `status` use today's
text alone.

**F-066 — an unprobeable component was kept as a name (HIGH, fixed).**
The resolver kept an `ERROR` probe as a plain name, the way it keeps an
absent component. But it probes the *resolved* spelling, and past 4096 bytes
readlink says ENAMETOOLONG. The kernel walks the short spelled path instead,
so a symlink there was invisible to hapi and followed by the write. The
failure was constructed with absolute texts only: a 4093-byte directory chain
reached through `~/.cfg`, then `esc -> /outside`. Now only an absent
component is kept literally; an error ends the walk with 0, which every
caller refuses.

**F-067 — rows were compared as spelled (HIGH, fixed).**
F-057's nested-row guard compared raw strings, and so did the parser's
duplicate check. Three spellings passed, and the inner row was written
through the outer row's new link, out of the scope:

- `./.x/inner`;
- `/.x/inner`;
- a user's `alias -> .x` with the row `alias/inner`.

Two spellings of one target passed the duplicate check, and the second
link replaced the first.

The planner now compares each row at its physical location. A row beneath
another row's place is refused as nested, and two rows at one place get a
new refusal, *two rows name the same target*.

One case no plan can see: `alias -> .x` where `.x` is the user's link to
`old`, and a `--force` row then replaces `.x`. So a backstop records each
row's physical place at plan time. Once the run has written anything, it
checks each later row again before writing it, and stops before one whose
place moved.

**F-068 — `--force` deleted the file before the link existed (HIGH, fixed).**
If symlink(2) then failed, the user's file was gone and nothing was
recorded. The failure was constructed with a link text over 4095 bytes.
On Linux the link is now made under `.hapi-new-<pid>` beside the target and
renamed over it. The agnos arm keeps the old order, because a real agnos
kernel cannot rename over a file (F-059).

**F-069 — a source that leads back to its target (HIGH, fixed).**
The source was only probed for presence, and a symlink counted as present
without being followed. These were constructed:

- `pkg/bashrc -> ~/.bashrc`, relative and absolute, with the row
  `bashrc -> .bashrc`: `--force` deleted the only copy and planted a loop
  that `status` called OK;
- a package directory link to `$HOME`;
- a source that holds its target: a directory cycle;
- an absent target: a self-loop, at exit 0;
- a source passing through its absent target and leaving by `..`.

`fsl_source_reaches` now follows the source physically and watches every
path the walk visits. A source that passes through its target, ends inside
it, holds it, or cannot be followed to an end is refused. `--force` does not
override this.

**F-070 — another package's files (HIGH, fixed).**
F-045 asked only about the current package. Constructed with absolute links,
so independent of F-065:

- with package A's `.config/nvim -> A/nvim`, `link --force B` with a row
  `.config/nvim/init.lua` deleted A's only copy while `status A` said OK;
- `adopt` moved A's file into B;
- one no-arg `sync` sent package bb's write into package aa's repository.

`link` and `adopt` now read the trail and refuse a target that physically
sits inside any package source it records.

Every link and adopt entry counts, unlinked or not. A package's files are its
own whether or not hapi's link to them still exists, and the test pins that
with a user's own link into an unlinked package. A trail they cannot read
stops them, as it already stopped `unlink`, `rollback` and `list`.

**What it costs.** The first version resolved every recorded source in every
process. A cold `sync` over the benchmark's 100 packages, one process each,
went from 137 ms to 789 ms, against the gate of 2×. Two changes bring it to
about 163 ms (+19%):

- `link` reads the trail only for a row whose target is reached through a
  symlink, the only way such a target lands in another package;
- a source is resolved only when its own name is a component of the target's
  physical path, since its place ends in that name.

Within one process the list is kept, and only the lines the trail has grown
by are read. A trail that is shorter, or is set again, is read from the
start.

**F-072 — the trail could live anywhere (HIGH, fixed).**
With HOME unset or empty, the trail fell back to `/tmp/.local/state`. A
relative `XDG_STATE_HOME` or HOME put it under the cwd. Either can be a
directory another local user owns, and their planted entries made `rollback`
create links in the victim's home. From any other cwd, `unlink` said the
trail was empty, at exit 0.

Now only an absolute base counts. A relative `XDG_STATE_HOME` is ignored, as
the XDG Base Directory spec requires. With no absolute HOME either there is
no trail: readers return `HapiArNoLocation`, writers fail their pre-flight,
and messages say why.

### Write paths

**F-071 — concurrent adopts destroyed a file (HIGH, fixed).**
adopt ran its checks with nothing held: no row has this source or target,
nothing sits at the package-side name. Its move was then a plain rename(2).
Two adopts deriving one name both passed, and the second replaced the first
one's file. The verifiers measured 34 losses in 200 runs. The 2026-10-28
record had listed this race as serialized by the lock; the lock never
covered the move.

adopt now holds the package lock from its manifest read to its trail entry.
It moves with `hapi_rename_noreplace`, which on Linux is link(2) then
unlink(2), so it never replaces a name. Its undo moves back the same way and
says when it could not, instead of printing `restored` regardless. The
harness races two adopts for 40 rounds: 1.7.0 lost a file in 6 rounds, 1.7.1
in none.

**F-073 — a manifest read could be cut (HIGH, fixed).**
`_hmw_slurp` took a failed read(2) as the end of the file, and took a file
whose size changed while it was read as whole. `adopt` and `fmt` then
committed a cut manifest, and `sync --prune` acted on half of one.

The read now fails on an error, and on any difference between the size it
began with, the bytes it read, and the size after. Every verb's manifest
parse goes through it: `hapi_mf_parse_file_r` now reads with it, then calls
the same `cyml_parse` that `cyml_parse_file_r` wraps. A short read is
constructed with a sysfs file that reports 4096 bytes and holds five.

**F-074 — a value with no closing quote parsed (MEDIUM, fixed).**
It was read to the end of the header, so a manifest cut mid-row parsed with
a truncated target. Now `a value has no closing quote`. A property test
checks every prefix of a three-row manifest: each either fails to parse or
holds only whole rows of it. No manifest ADR 0001 describes has an open
value; the ADR 0001 addendum records this.

**F-075 — `link` hashed a second read (LOW, fixed).**
`link` re-read the manifest to hash it, so the trail's `manifest_hash` could
describe rows other than the ones it applied. It now hashes the manifest it
parsed (`audit_manifest_hash_of`).

## Accepted boundaries, new

- **A writer that pauses across hapi's whole run with the size unchanged**
  is not detected by F-073's check. Only a size change, or a read that comes
  up short, is.
- **F-071 on a filesystem without hard links.** There the move falls back
  to a probe and a rename, which the package lock serializes against every
  other hapi, but not against another program.
- **A row that spells a path straight into another package's directory,** with
  no symlink in its chain, is not checked against the trail. It is the user's
  own choice of target, it was never refused, and it is still a conflict that
  needs `--force`.
- **F-067's backstop works inside one `link` run.** Across packages in one
  `sync`, F-070's trail check is what holds. The test pins that.
- **F-065's legacy text is accepted for removal only.** A link with it is
  `WRONG` in `status`, and a no-arg `sync` refuses the package until
  `hapi link --force <pkg>` rewrites it (CHANGELOG *Upgrading*).

## Mutation survivors

Each seeded revert of a repair turned the suite red, except the following.

| Mutant | Why it survives |
|---|---|
| The initial `_fsl_split` from byte 1 | Equivalent: the path it splits is always absolute. |
| adopt's lock with a plain rename, or no lock with the no-replace move | Each half alone closes the hapi-vs-hapi race the harness stages. Reverting both is 1.7.0, which the harness turns red. |
| The no-hard-link fallback's probe | Not reachable on the suite's tmpfs, which supports hard links. |
| `_hmw_slurp`'s read-error branch | Equivalent where the size check already refuses the read. Kept as a guard. |
| `link` hashing the file instead of the parse | Differs only under a concurrent writer. |
| F-070's component pre-check removed | Equivalent: it saves resolves without changing an answer. The benchmark row is its check. |
| F-070's unreadable-trail refusal, before the fixture was corrected | Killed once the test wrote exactly its bytes. |

## Refuted and unconfirmed

A finding whose two verifiers split, one PLAUSIBLE and one REFUTED, was kept
in the triage at its weaker reading, not dropped. The refuted readings that
matter:

- **rollback re-creating a link through a parent swapped out of the scope**
  sits inside the accepted boundary that rollback acts on the trail without
  re-checking the grant (2026-10-28).
- **Two trails, from cron versus the interactive shell,** is configuration,
  not a defect. It is recorded for the docs.

**Argv-surface golden.** 819 cases, compared on stdout, stderr, exit code,
resulting tree and trail. 1.7.0 and 1.7.1 are byte-identical in every case
apart from the version string. None of tier 1 is reachable from the golden's
fixture: each needs a symlinked layout the golden does not build.

**Differential argv fuzz.** 50,000 lines against 1.7.0, every one compared
byte for byte, since 1.7.1 adds no surface: no mismatch. The first run found
19. Each was `adopt` into a package directory that does not exist, which
reported a lock failure where 1.7.0 said `could not read manifest`, because
F-071's lock is now taken first. adopt parses the manifest before locking,
and the message is 1.7.0's again.
