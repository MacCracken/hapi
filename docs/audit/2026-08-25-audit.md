# 2026-08-25 — P(-1) hardening sweep (1.0.5)

**hapi version**: 1.0.5 (patch line; no surface change).
**Auditor**: maintainer pass per CLAUDE.md Process P(-1), run as a
multi-agent sweep — five independent read-only audit streams
(security, syscall/return handling, path validation + test coverage,
refactor/optimization, external research), an adversarial refutation
pass over the merged findings, and a completeness critic — then
verified by hand before any repair landed.
**Trigger**: the 1.0.4 toolchain refresh touched syscalls
(`hapi_readlink`), a path argument (`fs_link.cyr`'s `sys_open`) and the
audit-trail writer's allocation, all three of which the checklist names.

> ⚠ **This pass is materially different from its two predecessors.**
> 2026-05-23 and 2026-05-24 were re-walks of a surface believed sound,
> and both concluded with the four threat classes confirmed clean. This
> one found **nine HIGH-severity defects**, two of them heap overflows
> reachable from an ordinary manifest, and one capability escape that
> contradicts CLAUDE.md's load-bearing rule outright. The earlier passes
> were not wrong about what they checked; they checked the *validators*
> and did not check the *writers*. Every finding below is in a buffer,
> an argument parser, or a write path — the code the prior lens did not
> point at.

## Scope

The four standing threat classes (path traversal, symlink loops,
TOCTOU, capability boundary), plus the four remaining P(-1) steps:
cleanliness, benchmark baseline, internal review of every path argument
and syscall return, and external research against GNU stow and its
peers.

## Method

Findings were only accepted with a **constructed failure** — concrete
inputs, run against a real build, producing the stated wrong outcome.
Everything else was refuted and is listed as such, so the next pass does
not re-derive it. Nine claims were killed this way, including two that
read convincingly from the code (a phantom `unlink` trail entry, and a
`w == 0` write loop that POSIX makes unreachable on a regular file).

Each repair below was **mutation-proven**: the new regression test was
run against the unfixed code and confirmed RED before the fix landed.

## Findings — fixed in 1.0.5

### F-008 — audit entry composers ignore `cap` [HIGH] — FIXED

`_audit_format_link_op` and `audit_format_rollback_marker` accepted a
`cap` argument and never read it; `_audit_emit_field` wrote unbounded
into the caller's fixed `alloc(4096)`. Both bounds are attacker-sized:
`target` and `abs_target` come from the manifest, and the JSON escaper
expands a control byte 6:1.

*Constructed*: a manifest target of 19 × 200-character components (a
legal path) composed an **8,027-byte** line into a 4,096-byte buffer.
The same target made of `0x01` bytes composed **46,028 bytes** — a
~42 KB out-of-bounds heap write of attacker-chosen content. Worse, the
post-format `audit_ensure_dir()` bump-allocated *on top of* the already
formatted bytes, so the line reaching disk contained spliced heap
content and a raw NUL. `link` exited 0; the trail no longer parsed as
JSON; `unlink` then reported `unlinked 1 / 1` while the symlink
remained on disk.

*Fix*: bounded writers (`_audit_put8` / `_audit_putn`) with an overflow
flag, and `audit_entry_size` sizes each append buffer from its own
inputs. An entry that cannot fit **refuses** — `_audit_append_bytes`
maps the −1 to `Err(HapiAuditWriteFailed)`, which is already the
enumerated `hapi: audit-trail write failed` / exit 1 path. Refusing,
never truncating: a short line has no `\n`, so the next entry
concatenates onto it and the reader drops both. Post-fix, the 8,030-byte
entry is well-formed JSON with no NUL, and the 46,030-byte one composes
correctly.

### F-009 — `_hmw_slurp` truncates a manifest at 256 KB, and the rewrite commits it [HIGH] — FIXED

`_hmw_slurp` read into a fixed `alloc(262144)` and stopped at the cap
with **no signal**, and both callers hand the buffer straight to
`_hmw_write_atomic`. ADR 0001 sanctions an arbitrarily long markdown
body below the `---` separator, so the size is reachable without the
user doing anything unusual.

*Constructed*: a 300,109-byte manifest, `hapi adopt` → exit 0, manifest
permanently truncated to the cap, markdown body and everything after it
destroyed via `tmp` + `rename`.

*Fix*: size the buffer from the file (`xlseek` SEEK_END), with one byte
of headroom so a file that grew mid-read is caught and refused rather
than committed short. Post-fix the 300 KB manifest survives an adopt
intact with the row appended.

### F-010 — `--backup-to` silently destroys one snapshot on a basename collision [HIGH] — FIXED

The destination is `<ts>-<pkg>-<basename>`, so two manifest rows whose
targets share a basename (`a/config`, `b/config`) compose the **same**
path within one second. `O_TRUNC` meant the second copy overwrote the
first — destroying exactly the bytes `--force` was about to delete —
and both audit entries recorded `backup_path` pointing at the survivor,
so the trail actively misstated where the lost content was.

*Fix*: the composer probes and suffixes `-2`, `-3`, … until the name is
free, so the earlier snapshot survives and each trail entry names the
file that actually holds its bytes; and the copy opens the destination
`O_EXCL` rather than `O_TRUNC` as the backstop for the residual race.
Verified: both originals recoverable, two distinct `backup_path` values
in the trail. Two adjacent LOW repairs rode along — a `w == 0` write
result is now an error rather than a silent spin, and the write-side
`file_close` return is captured (a deferred write error on the last
copy of the bytes must not be reported as success).

### F-011 — `adopt` applies no capability bound to its `<file>` argument [HIGH] — FIXED

`adopt` renames the file away and plants a symlink where it stood — its
`<file>` argument is a write target — but it was never capability
checked.

*Constructed*: `hapi adopt /path/outside/$HOME/target.conf pkg`, **no
`--root`**, exit 0: the file was moved out of its directory and a
symlink planted in its place, both outside `$HOME`. That is a direct
violation of CLAUDE.md's *"Do not write outside `$HOME` without an
explicit `--root` flag — the capability boundary is load-bearing."*

*Fix*: new `cap_within_scope(path, scope_root)` in `src/cap.cyr`
(lexically normalizes both sides, then component-boundary match), called
in `cmd_adopt` immediately after the target resolves. Verified: the
absolute escape and the `../` escape both refuse with exit 1 and leave
the file untouched; a file inside `$HOME` still adopts; and a path
outside `$HOME` **with** a `--root` grant still adopts, so the
capability grant keeps working.

### F-013 — every verb silently ignored extra positional arguments [HIGH] — FIXED

*Constructed*: `hapi rollback totally-bogus-package-name` — a user
trying to scope a rollback to one package — ignored the argument and
**reversed the entire visible trail**, destroying all three links, exit
0. The same shape made `hapi link A B` report complete success having
linked only A.

*Fix*: `_hapi_extra_arg` and an `else` arm on every verb's parse loop.
Verified across the surface: `rollback <pkg>`, `link A B`,
`checkpoint X`, `list X`, `inspect A B`, `unlink A B` all now exit 2
with a named diagnostic, the three links survive, and every legitimate
form (`rollback --dry-run`, bare `list`) still exits 0.

### F-014 — `hapi_mf_canonicalize` ignores `cap` [HIGH] — FIXED

The function accepted `cap` and never referenced it; its own doc comment
said *"Caller is responsible for sizing `out` generously (64 KB is
plenty for realistic manifests)"* — an unchecked assumption.

*Constructed*: a 3,000-row manifest (138 KB, well under the cyml read
cap) → `hapi link`, `hapi sync` **and `hapi link --dry-run`** all died
with **exit 139** (SIGSEGV), outside the published 0/1/2 contract, with
no diagnostic. `--dry-run` is not spared because the hash is computed
before the dry-run branch. The overflow lands on the `sorted` vec the
row loop is iterating, so the faulting pointer is built from manifest
bytes.

*Fix*: bounded writers plus `hapi_mf_canonical_size` sizing the caller's
buffer. Refuses rather than truncating — these bytes are the `sha1c:`
`manifest_hash` preimage frozen by ADR 0002, so a short prefix would
quietly hash a different document. Post-fix the 3,000-row manifest
**links successfully**. The canonical bytes are unchanged for every
manifest that already fit: asserted by the exact-size byte-comparison in
the new test, by the four standing canonical-hash groups, and by the
benchmark's audit output being byte-identical at 101,150 bytes.

## F-002 — re-scoped, then FIXED in 1.0.8 [MEDIUM]

`cap_check_root_r` remains lexical-only. Two things about the deferral
are now wrong and are corrected here:

**1. The owner was never going to deliver it.** ADR 0005 parks the fix
on *"when kavach exposes a stable `cap_check(scope, action)` surface"*.
kavach is at **3.12.3** — long past stable — and is a **sandbox
execution framework**: ten backends, strength scoring, externalization
scanners, credential proxy, HMAC audit chain. Its entire public path
surface is `kavach_path_exists`. There is no capability or
path-resolution API, and none is planned. Adopting it would also collide
head-on with hapi's hard *no process spawning* rule. **The dep gate is
void**; F-002 is hapi-owned work.

**2. The scope was too narrow.** The deferral text covers *the `--root`
value*, and its rationale leans on the user having typed an explicit
escape flag. That does not cover the flagless case: a symlinked
*intermediate component* of an ordinary `$HOME` target (`~/.config ->
/mnt/other/etc`) escapes the scope on a plain `hapi link`, with no flag
at all. Re-scope to *"every path hapi derives from the scope root."*

The primitive the real fix needs now exists in hapi: `hapi_readlink` is
portable across all three targets as of 1.0.4. The pinned stdlib exposes
no `openat2` / `RESOLVE_BENEATH`, so the shape is a per-component
`readlink` / `O_NOFOLLOW` walk. Not attempted in 1.0.5: it changes the
result of a resolver that four verbs use to *prove ownership* by
recomputing and byte-comparing, so it needs its own arc.

## Accepted boundaries

- **`--backup-to`'s destination is deliberately not capability-bounded.**
  It is an explicit, user-typed flag naming a specific directory, and
  1.0 users legitimately point it at `/tmp` or an external drive; gating
  it would break working setups. Revisit at 2.0. (F-020 is a separate
  matter — there the *package*, not the user, picks the destination.)
- **`unlink` / `rollback` act on the trail-recorded `abs_target` without
  re-checking the capability grant** that authorised the original write.
  "We only remove what we created" is defensible, and re-checking would
  refuse reversals 1.0 performs — but ADR 0005's stated rationale for it
  is factually wrong and needs correcting.
- **`hapi checkpoint` is not idempotent**: three consecutive checkpoints
  append three markers. Defensible as journal semantics, but unstated,
  and it is free growth toward F-007's reader cap.
- **Entries longer than PIPE_BUF (4096 bytes) cannot retain ADR 0002's
  single-write append atomicity**, even now that F-008 sizes the buffer
  correctly. Growing the allocation fixed the out-of-bounds write, not
  the atomicity premise. Additive note for ADR 0002; the line shape and
  required-field set are unchanged.
- **F-005 (single-process TOCTOU) stays accepted but is mis-scoped**:
  the multi-process case is where the damage is, and it is not a TOCTOU
  — it is F-012's unlocked read-modify-write.
- **F-001, F-003, F-004 and F-006 are unchanged and still hold.** F-003
  holds on Linux/macOS; see F-031 for agnos.

## Refuted

Recorded so a future pass does not re-derive them: a phantom `op:unlink`
entry on a corrupted trail (the code explicitly declines to audit a
no-op); a 75-row "silent OOB window" in canonicalize (the real window is
~9 bytes); an unmapped-page crash mechanism (the allocator's chunk is
256 MB, so the byte past the buffer is mapped); a `w == 0` infinite loop
(unreachable on a regular file per POSIX — fixed anyway); a 32-byte
`getdents` buffer misclassifying a directory (unconstructed); a NUL
truncating a recovered path in `_har_read_str` (unconstructed); and
`--backup-to` as a capability violation *per se* (it is an explicit
user-typed flag). Several performance deltas from the refactor stream
could not be reproduced and are not carried.

## Sign-off

Six HIGH findings fixed in 1.0.5, each with a mutation-proven
regression test; F-007, F-016, F-017 and F-012 followed in 1.0.6 —
closing both Tier 1 items of the arc — and F-021 and F-028 in 1.0.7,
finishing the manifest write path. **Fourteen** remain open and
documented above rather than quietly carried.
The v1.0 contract is untouched: the command surface, ADR 0001's manifest
schema and ADR 0002's audit-trail format are byte-identical, and every
repair is contract-safe. **1.0.5 is safer than 1.0.4 and is not yet
clean** — the honest reading is that this pass converted an unexamined
write path into a known one, and the next arc owns F-007, F-012 and
F-015.
